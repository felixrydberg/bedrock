# Stateful compute on Bedrock — plan v2

Status: accepted plan (decision 16), tracked as issues #109–#127 and #131. Nothing here is implemented yet. Drafts use `S-NN` IDs so they don't collide with the `B-NN`
drafts in [`feature-drafts.md`](../feature-drafts.md). When a draft becomes a GitHub issue, link it here and keep the
GitHub number next to the plan ID, as `feature-drafts.md` does.

## 1. Goal

Build a Workers-style platform with Cloudflare's bindings (Durable Objects, D1, Queues, Cron Triggers, Alarms,
Workflows, KV) by following the Rivet / OpenOrange approach: **one actor primitive and everything stateful built on
it**, customer KV included. Each KV namespace's writer becomes an actor, without SQLite; `bedrock-kv` keeps KV's read
side (S-18).

| Cloudflare binding | Runs on Bedrock as |
| --- | --- |
| Durable Objects | One actor per object, with its own SQLite database |
| D1 | One actor per database, running a built-in SQL handler |
| Queues | One actor per queue |
| Cron Triggers | One actor per Worker, using that actor's alarm |
| Alarms | A field on every actor, fired by its holder or by its storage |
| Workflows | One actor per instance; the engine is runtime code on top of DO and alarms |
| KV | One actor per namespace, with key/value entries instead of SQLite pages; `bedrock-kv` keeps the per-cell value caches (S-18) |
| R2, Email, AI, Sandboxes | Out of scope |

Two new binaries do the work:

- **`bedrock-compute`** runs Workers and every actor, with no local state.
- **`bedrock-volume`** stores actors: quorum-replicated SSD logs in front of one S3 database per hash range, shared by
  many actors.

Quicksilver, the CDN, relays and `bedrock-api` keep their current jobs. The Gateway (B-57) gains an actor-routing
module, and `bedrock-kv` hands its namespace writers to Compute.

## 2. What differs from the core Bedrock rules

Each item below loosens or changes a recorded decision. They are listed in §10 for confirmation.

- **Leases with heartbeats are allowed** in this subsystem, for one purpose only: proving that an actor's holder is
  still alive. Cluster membership still comes from relay streams (decision 4).
- **A whole-DC outage means downtime** for actors homed in that DC. A cell outage must not cause downtime when the DC
  has at least three cells.
- **Actors belong to a region by their ID** (`eu_…`). Inside the region, the DC, cell and host are computed from the ID,
  so no lookup is needed. Only the holder of an awake actor is recorded, in its storage.
- **Writes are acknowledged by a quorum of SSDs** (2 of 3, in different cells of one DC). S3 is never on the write path.
  This includes customer KV: its writers are actors from the start, and B-26's acknowledge-after-S3 owner path is not
  built (§10 item 7).

## 3. Binaries

| Binary | New? | Job in this plan | Membership |
| --- | --- | --- | --- |
| `bedrock-compute` | New (planned in decision 15) | Worker sandboxes; actor host (lifecycle, SQLite VFS, volume client, gates, alarms while held); built-in D1, KV, Queue and Cron handlers; bindings | `compute.{cell}` |
| `bedrock-volume` | New | Actor storage: claims, leases, quorum log, key/value overlay, SSD cache, flushes to S3, alarm index for sleeping actors | `volume.{cell}`, hash ranges per cell |
| `bedrock-gateway` | Planned (B-57) | Plus actor routing: region → DC → cell → host, a location cache, wake | as in B-57 |
| `bedrock-quicksilver` | Exists | Topology, actor namespace, D1, queue and cron records (in `infrastructure`) | unchanged |
| `bedrock-kv` | Exists | KV read side: per-cell value caches, the REST API and namespace management. Namespace writers move to Compute (S-18) | unchanged |
| `bedrock-cdn` | Exists | Worker bundles (B-35) | unchanged |
| `bedrock-relay`, `bedrock-api` | Exist | Membership and placement for `compute` and `volume`; Quicksilver writes | unchanged |

**Why two binaries and not one or three:**

- Putting storage on compute hosts would make compute stateful: scaling would move data, and one tenant's CPU load
  would slow every actor's commits on that host.
- A separate directory or placement service is unnecessary because placement is computed (§4) and the authoritative
  claim lives with the data (§5). There is no pegboard-style actor database to run.
- D1, Queues, Cron and Workflows run as code inside Compute, not as services of their own.

Membership, health and placement stay per cell. Compute and volume join their cell relay like every other service
(B-12). Volume uses the relay-assigned hash ranges of decision 13, with handoffs (B-21).

## 4. Actor identity and placement

### IDs

`{region}_{base32(128 bits)}`, for example `eu_c2q7v…`. The region code must be listed in Quicksilver's topology,
otherwise the ID is rejected.

- `idFromName(name)` takes the first 128 bits of SHA-256(`namespace_id` ‖ `name`), using the binding's region (its
  jurisdiction, or the namespace's default region).
- `newUniqueId()` uses `bedrock_lib::uuid()`.
- A D1 database ID and a queue ID use the same format and are chosen when the resource is created.
- Storage and routing keys always carry `(actor namespace, actor ID)`, so an ID from one namespace never reaches
  another namespace's data.

### Placement functions (`lib/actors`)

All of these are pure functions of the ID and the topology record. The topology record is static Quicksilver config:
`topology/region/{code}` lists the region's actor DCs and each DC's cells.

| Function | Result | Changes when |
| --- | --- | --- |
| `region_of(id)` | The ID prefix | Never |
| `dc_of(id)` | Rendezvous top of the region's DC list. Not filtered by health. | A DC is added to or removed from the region (S-17) |
| `cells_of(id)` | Rendezvous ranking of the DC's cells | A cell is added to or removed from the DC (with joint majorities, see §5 Single writer) |
| `slots(id)` | Three replica slots: the first three cells of `cells_of`. If the DC has fewer cells, the list wraps around and gives the same cell slot 1 or 2. | as above |
| slot → node | In the slot's cell, the owner at that slot index of the range holding `hash(id)` in the `volume` directory. A cell's volume ranges have `R = ceil(3 / cells in DC)` owners in distinct failure domains. | Ordinary range handoff in that cell (B-21) |
| wake host | Rendezvous over the healthy `compute` members of the first healthy cell of `cells_of`, weighted by capacity | Membership. This only chooses where to **wake**; it never moves an awake actor. |

`dc_of` ignores health on purpose. Moving an actor to another DC would need a fence across DCs, and the accepted cost of
a DC outage is downtime. Waking compute in the first slot cell keeps one replica local, so a commit waits for one
cross-cell acknowledgement.

## 5. Storage: `bedrock-volume`

The design follows Rivet's Depot volume, but each piece reuses something Bedrock already has.

### Records on a slot

The records live in RocksDB through the existing `lib/storage` adapter. Keys start with the big-endian hash, as in
L2 storage, so a range is one scan and dropping it is one `delete_range` (decision 13).

- `{hash}{actor}/claim`: epoch, holder (cell, host), state (`held` or `released`), committed sequence, alarm time, and
  the sequence that is durable in S3.
- `{hash}{actor}/log/{seq}`: one commit, with its epoch, sequence, `committed_at`, a batch of key/value changes and
  the alarm change. The batch is the `Changes` type that `NamespaceDatabase::write` already takes. The volume never
  reads the keys: for SQLite they are page numbers, and for KV they are customer keys.
- `{hash}{actor}/data/{key}`: the newest value, or a delete, of each key written since the last S3 flush (the overlay).
- `alarm/{when}{hash}{actor}`: a time-ordered index used only for released actors. It is removed with its claim.
- Each commit is one atomic RocksDB batch: log entry, overlay changes and claim sequence together. RocksDB's synced WAL
  group-commits concurrent batches into one fsync, which is the B-65 property without writing a log store.

### Protocol

The holder (a Compute host) is the only writer and acts as its actor's sequencer. Bedrock calls this an appointed
writer: there is no Raft group and no election per actor.

- **Reserve.** The host first sends `Reserve(actor, epoch = highest seen + 1)` to all three slots. A slot accepts only
  an epoch above its highest reservation and fsyncs it. Once two slots have accepted, no other host can reserve that
  epoch, and the reservation survives the loss of any one slot's disk (S-02b, #131). A refusal names the slot's
  reservation, and the host retries above it.
- **Claim.** The host then sends `Claim(actor, host, epoch)` at the reserved epoch to all three slots. A slot accepts
  only if the epoch is higher than its own and no other holder has a live lease (see Lease below). Each answer carries
  the slot's log end.
  - With two acceptances, the host takes the most advanced log: highest entry epoch first, then highest sequence. It
    copies any missing tail to the lagging slot, then appends a no-op at the new epoch. The actor is open once that
    no-op reaches the quorum. This is Raft's Figure 8 rule, as in B-64.
  - A rejection names the live holder, and the request is redirected there.
- **Append.** A commit becomes one entry `(epoch, seq, changes)`, sent to all three slots in parallel. A commit is an
  SQLite `xSync`, or a KV write or bulk write. A slot
  writes it only if the epoch matches its claim and the sequence follows its log. The commit is acknowledged after
  two slots fsync it.
  - The host pipelines entries within a bounded window, and a slow slot does not hold up the quorum.
  - Each entry carries the writer's `committed_at` unchanged through every hop.
- **Lease.** Each Compute host sends one heartbeat per second to each volume node where it holds actors, not one per
  actor. A slot treats an actor's lease as live while it has seen the holder's host within 5 seconds, measured with
  `monotonic_now()`.
  - The holder stops serving an actor (self-fences) when fewer than two of its slots have acknowledged a heartbeat
    within 4 seconds.
  - Epochs fence storage writes whatever the clocks do. The lease protects only the single-instance guarantee for
    in-memory state, and assumes that clock rates drift by a bounded amount.
- **Read.** On a cache miss, the holder calls `Read(actor, keys, min_seq = committed seq)` on the nearest slot.
  - The slot answers from its overlay, then its SSD cache, then S3.
  - A slot that is behind `min_seq` refuses, and the holder tries the next slot. A read is filled only from a source at
    least as far along as the caller.
  - For SQLite, a miss returns the whole 64-page chunk around the page, to prefetch it.
  - `Scan(actor, start, limit, min_seq)` returns keys in order, merging the slot's overlay with the S3 database. KV
    `LIST` uses it.
- **Release (sleep).** The host appends a `Release` entry. After that, a new claim needs no lease wait. Neither sleep
  nor wake touches S3.

### Single writer

The volume enforces the single-writer guarantee. Compute cannot get around it, and Gateways, routing tables and
location caches are only hints (B-66). There are four writers to fence, and each has one mechanism.

| What could get a second writer | Fence | Where |
| --- | --- | --- |
| Durable state: the quorum log | Epochs | Volume slots |
| In-memory state: answers that need no write | Lease | Volume slots and the holder |
| S3 | SlateDB writer fencing, and flushing only committed entries | Range maintainer |
| Inside one host | One instance per actor | Compute's actor host |

- **Epochs (the hard guarantee).**
  - A slot promises an epoch when it accepts a claim. It accepts a claim only above its promise, so two claimants
    never both win the same epoch.
  - It accepts an append only at its current promise. Once two slots promise `e + 1`, an append at `e` can reach only
    one slot and never commits.
  - Every claim quorum shares a slot with every commit quorum, so the new holder recovers every acknowledged commit.
  - This is Raft's term rule with an appointed leader (B-64), and it holds whatever the clocks do.
- **Lease (single instance).** A fenced holder can't commit, and its output gate holds every response that waits on a
  commit. A request that writes nothing, though, could still be answered from stale memory.
  - The lease closes that gap. Slots refuse a claim while the holder's heartbeat is live (5 s), and the holder
    self-fences first (4 s).
  - This assumes clock rates drift by a bounded amount. If an actor kind needs no clock assumption, it can confirm with
    a quorum before answering instead, at one round trip per request.
- **S3.**
  - SlateDB fencing leaves one maintainer able to publish.
  - A maintainer flushes only through the commit point the current holder announced. It learns that point with appends
    and heartbeats, as in Raft's leader commit index.
  - A slot can hold an uncommitted tail from an old epoch at the same sequence numbers. Recovery truncates that tail
    before the slot accepts new appends, so it never reaches S3.
- **Inside one host.** The actor host keeps one instance per actor ID. `Acquire` joins a wake already in progress
  instead of starting a second one.

Three changes move votes. Each must keep every new quorum sharing a slot with every old one:

1. **Range handoff inside a cell** (slot → node). The leaving owner seals the range and refuses claims and appends. The
   populating owner then copies from it and votes only after that. While this runs, the slot is unavailable and the
   actor runs on its other two slots.
2. **A slot that lost its data** (crash, wipe). Its replacement copies from both other slots and votes only after a
   newer claim has committed (§5 Slot repair).
3. **A cell added to or removed from the DC.** This changes `slots(id)`. The topology record carries a version, and
   claims and appends carry the version they used.
   - During a transition, a commit needs a majority of the old slot set and a majority of the new one (Raft's joint
     consensus).
   - Slots refuse a version older than their own.
   - Actors whose first slot moves get their keys copied to the new first slot's range database (§5 Cold tier).
   - A DC change (S-17) is the same at DC level: the new DC claims only after the old DC has released the actor and
     flushed it.

### Cold tier

Changed 2026-11-14 (user decision): one SlateDB database per `volume` range, holding many actors, replaces one
database per actor. Per-actor databases made S3 requests grow with the number of actors, which high-churn workloads
(agents, sessions, jobs) cannot afford. The SSD tier stays a fast acknowledgement cache, and data still reaches S3
within about a second.

Each `volume` range of each cell has one S3 database through the B-11 namespace contract (SlateDB), which reuses
fencing, checksums and GC protection. It holds the actors in that range whose **first slot** (`slots(id)[0]`) is in
that cell, keyed by `{hash}{actor}/…`, so actors are isolated by key prefix. Each actor is therefore in exactly one
database, not three.

- **Maintainer.** The owner of an actor's first slot is its maintainer, so one node writes each range database. It
  batches overlay changes of every actor in the range that changed, each up to its own sequence `S` (at most that
  actor's announced commit point), into one atomic SlateDB batch with each actor's `meta.seq = S`. After the flush is
  durable, it tells each actor's slots to truncate the log and overlay through `S`.
- **When.** A range flushes every second or every 4 MiB, whichever comes first. A DC that is lost for good therefore
  loses at most about a second of acknowledged writes, as decision 7 (§10) assumes, plus whatever piled up while an
  actor's first-slot range had no ready owner (S-17 documents the bound). Release does not flush: neither
  sleep nor wake touches S3.
- **Cost.** About two S3 writes (one data file and one manifest update) per busy range per flush, plus compaction. The
  cost grows with ranges and bytes written, not with the number of actors, so billions of small actors are fine.
- **SlateDB settings.** SlateDB's own WAL is off (the `wal_disable` feature): the SSD quorum log already is the
  write-ahead log, and the maintainer calls `flush` on its own timer. SlateDB's per-prefix segments (RFC-0024) are not
  used, because a segmented flush writes one file per changed segment, which would bring back per-actor S3 writes.
- **Handoff.** When a range moves to another node, the new owner opens the same database once it is ready, and SlateDB
  writer fencing stops the old owner. No data is copied. While the range has no ready owner, its flushes pause; commits
  continue on the other slots.
- **Split and merge.** Splitting or merging a range splits or merges its database with SlateDB's clone, which builds new
  databases from the old files for a key range without copying data (S-05, S-19).
- **First slot moves.** A cell added to or removed from the DC changes `slots(id)[0]` for some actors. As part of that
  transition, their keys are copied into the range database of their new first slot before the old one drops them.
- **S3 reads.** The other slots read the range database through #73's read-only `Reader`, which never fences the
  writer. #73's `Readers` residency (open on demand, a cap on open handles, least recently used first, idle close)
  moves from `kv/storage` to `volume/cold` in S-05, keyed by range database instead of by home-region namespace.
- **SSD cache.** Volume nodes keep a bounded, droppable cache of values read from S3, with Foyer as in B-30. This is the "SSD
  layer in front of S3".
- **Deletion.** Deleting an actor tombstones its claim and, after a grace period, deletes the actor's key prefix in its
  range database. Compaction reclaims the space.
- **Not yet.** Point-in-time recovery would use SlateDB checkpoints later, per range.

### Slot repair and range handoff

- A new range owner starts as `populating` and **does not vote**. It copies claims, logs, overlays and alarms for the
  range from the actor's other slots. Those slots are in other cells with other range boundaries, but the hash-first
  layout makes each copy one scan per peer.
- It becomes `ready` only after copying from every voting peer. If an empty slot voted, the old quorum and the new
  quorum could share no member that knew the latest epoch.
- **Range handoff.** The new owner votes once it is ready. It copied from the sealed leaving owner, which refuses
  claims and reservations after sealing, so it holds every promise that slot gave.
- **Repair after a lost disk** (S-02b, #131). Copying from the peers does not restore promises the lost disk gave
  itself.
  - The repaired slot keeps the highest reservation it copied as its floor. It then waits as `repaired`, like Depot's
    learners: it takes claims and appends but counts towards no reservation, claim or commit quorum.
  - It votes again once a claim above its floor has committed its no-op, which it learns from that claim's appends.
    Every lost promise was for a reserved epoch at or below the floor, so that claim outranks them all.
  - `docs/spec/volume.md` keeps the traces that show why copying alone, or waiting without reservations, loses an
    acknowledged write.
- Readiness of a `volume` range is reported by the node and checked by its relay. The B-21 readiness rule assumes
  relay-streamed data, so this is a relay protocol change and goes into the specification first.

### Alarms

Whoever holds an actor runs its alarm, using an in-memory timer on the host. A released actor's alarm sits in the volume
index.

- The maintainer slot scans the index for its ranges and sends `Wake(actor, alarm)` through the DC's Gateway, the same
  path as a request.
- Other slots fire too if the alarm is still pending 5 seconds late.
- Delivery is at least once, retried with backoff as in Cloudflare. The handler's commit clears or reschedules the
  alarm.

## 6. Routing and wake

```text
client / Worker ──► Gateway (any tier) ──► region of id ──► dc_of(id) ──► cell ──► host
                                                                         │
                                    location cache hit ──────────────────┘
                                    miss: cells_of(id) first healthy → wake host
                                    host: running → serve │ free → Claim → wake │ held → Redirect(holder)
```

1. A **public request** (DO over HTTP or WebSocket, or the D1 HTTP API) enters any Gateway. A **Worker binding call**
   leaves `bedrock-compute` for its cell Gateway on the internal listener. The host runtime has already checked the
   binding (decision 15).
2. The Gateway reads the region from the ID and forwards through the upper tiers, as in decision 15, until it reaches
   a Gateway of `dc_of(id)`.
3. The DC or cell Gateway checks its location cache (actor → cell and host). The cache is a bounded LRU, learned from
   responses and redirects and dropped on failure. On a miss, it picks the wake host from §4.
4. The host's `Acquire` either serves the running actor, claims and wakes it, or returns `Redirect(holder)`. The Gateway
   follows at most two redirects, then answers with a retryable 503.
5. Waking reads `actor_ns/{namespace}` from Quicksilver to find the Worker and class, then the active deployment
   (B-50), then the bundle from the CDN (B-35). It starts the sandbox, and pages load lazily.

The hot path costs one hash per tier and a cached location. A cold start adds intra-DC quorum round trips for the
epoch reservation, the claim and its no-op, a sandbox start and the first page reads. No step reads a directory.

Deploys: an awake actor finishes its current events and restarts on the newly active deployment, as Cloudflare does.

## 7. Failure behavior

| Failure | Effect | Recovery |
| --- | --- | --- |
| Compute host dies | Its actors are unavailable until their leases expire (≤ 5 s) | The next request claims the actor on the wake host and recovers from the slots |
| Holder partitioned from its slots | It self-fences within 4 s | Same as above; stale appends are rejected by epoch |
| Volume node dies | Writes continue on 2 of 3 slots | The range is reassigned; the new owner populates, then votes |
| Cell dies (DC has ≥ 3 cells) | Leases there expire; each actor loses at most one slot. Actors whose first slot is there stop flushing, so their unflushed tail grows | Gateways skip the cell; wake hosts come from the next cell. Flushes resume when the cell returns; the overlay budget applies backpressure meanwhile |
| Cell dies (DC has < 3 cells) | Actors with two slots in that cell lose their quorum | Downtime until the cell returns, as for a DC |
| DC dies | Downtime for actors with `dc_of` = that DC | The DC returns. If it is lost for good, an operator restores from S3, losing at most the unflushed tail (S-17) |
| S3 unavailable | Commits and wakes continue; flushes back up | Backpressure once the overlay or log budget fills, and cold-page reads fail with explicit errors |
| Gateway location cache stale | One redirect or failed attempt | The cache is refreshed |

Safety never depends on discovery being current (B-66): a stale table or cache costs a redirect or a retry, never a
second writer.

## 8. Products on actors

All of these run inside `bedrock-compute`, using the actor host from S-07.

- **Durable Objects (S-10).** A DO is a class in a Worker bundle. `env.NS.get(id)` returns a stub, and
  `fetch`/RPC go through the Gateway to the holder.
  - Storage offers `ctx.storage.sql` plus the KV API, which is a hidden SQLite table, as in Cloudflare's SQLite-backed
    DOs.
  - The **input gate** lets one event run at a time across storage awaits. The **output gate** holds responses until
    their commit has its quorum acknowledgement, which takes a millisecond or so because S3 is not involved.
  - An actor sleeps after 10 seconds with no events and no open connections.
- **D1 (S-11).** Actor kind `d1` runs a built-in handler that executes statement batches as transactions. It serves
  the binding and the public HTTP API, with Cloudflare's limits for compatibility. Read replicas come later.
- **Queues (S-12).** A queue is one actor whose messages are SQLite rows.
  - `send` is acknowledged on commit.
  - Delivery batches messages (`max_batch_size`, with `max_batch_timeout` as an alarm) and invokes the consumer
    Worker's `queue()` on any Compute host.
  - Each message is acked or retried with a delay alarm. A dead-letter queue is another queue actor.
  - Throughput is limited to one actor per queue. Sharding waits for measurements.
- **Cron Triggers (S-13).** One actor per Worker holds all of its schedules and has its alarm set to the next fire
  time. It invokes `scheduled()` and records the last run. Deploy activation (B-50) sends it the schedules, and Worker
  deletion destroys it.
- **Alarms (S-09).** Native, as described in §5.
- **Workflows (S-14).** One actor per instance. Steps are memoized in SQLite, and `step.sleep` sets an alarm. The engine
  is JS runtime code, as in OpenOrange; Bedrock supplies only DO and alarms.
- **KV (S-18).** Each namespace's writer is an actor of kind `kv`, run by a built-in Rust handler with no SQLite and no
  sandbox.
  - **ID.** `{home_region}_` followed by 128 bits of SHA-256(namespace ID). The region is the namespace record's
    `home_region`, Cloudflare's jurisdiction.
  - **Writes.** A Worker's `put`/`delete` and the REST API's value and bulk writes go through the Gateway to the holder.
    Each becomes one entry, so a bulk write stays atomic. The holder checks Cloudflare's limits and the
    `storage_bytes` quota, and keeps retry results (24 h) and event retention (60 s) in the same batch. The closed
    PR #74's branch has both, ready to reuse.
  - **Revisions.** The holder keeps the namespace revision as its own counter, carried in each entry. Only data
    entries increase it, so claim no-ops leave no gaps.
  - **Reads.** These start at `bedrock-kv`: optional L1, then the cell value cache (#73's `ValueCache`) by HRW over
    `(namespace, key)` with a 60-second TTL. A miss goes to the holder, which also answers minimum-revision reads and
    `LIST`.
  - **Sleep.** Like any actor, the holder sleeps when idle. A cold miss wakes it.
  - **Expiry.** Expiration stays enforced on read, and compaction reclaims expired values. KV needs no alarms.
  - **What stays in `bedrock-kv`.** Value caches, the REST API front and namespace management (#72, #73).
  - **No migration.** No KV writer runs before S-18, so there is no cutover and no old owner to fence.

## 9. Code structure

```text
crates/
├── lib/
│   ├── actors        # ActorId parsing and formatting, kinds, placement functions (§4)
│   └── proto/volume.proto   # Claim, Append, Heartbeat, Read, Release, Truncate, Repair
├── volume/           # bedrock-volume
│   ├── store         # RocksDB records and atomic batches (§5)
│   ├── serve         # volume gRPC service and owner checks
│   ├── cold          # maintainer: SlateDB flush, truncation, cold reads, SSD cache
│   ├── alarms        # due-alarm scan → Wake through the Gateway
│   └── repair        # populating catch-up, range readiness
├── compute/          # bedrock-compute
│   ├── sandbox       # Worker runtime (choice open, §12)
│   ├── actors        # host: acquire, claim, sleep, gates, leases; vfs: SQLite over the volume client
│   ├── bindings      # KV, DO, D1 and Queue bindings, checked outside the sandbox
│   └── builtin       # d1, kv, queue, cron handlers
└── gateway/actors    # inside the B-57 crate: region/DC/cell/host routing, location cache, wake
```

- The volume client (sequencer, window, repair) lives in `compute/actors`, because only Compute writes.
- `tests/sim` boots both `run` functions, as it does for the other binaries.
- `volume` and `compute` depend only on `lib`.
- Quicksilver schemas are owned by their consumers:
  - `topology/region/{code}` (§4)
  - `actor_ns/{id}`: Worker, class and kind
  - `d1/{id}` and `queue/{id}`: owner, settings and consumer
- All of these go in the fixed `infrastructure` namespace.

## 10. Changes to recorded decisions (accepted by the user 2026-11-13)

These are recorded in `feature-drafts.md` decisions 4, 5, 11, 12, 15 and 16 (2026-11-14). Issues are amended when they are next touched.

1. **Decision 4 (no heartbeats).** Allow host-to-volume lease heartbeats for actors only. Membership is unchanged.
2. **Decision 5 (cell independence).** An actor's three slots span the cells of one DC. Each cell still decides its own
   placement. Only the data plane crosses cells, and each slot's owner comes from its own cell's directory.
3. **Decision 15 (no cross-cell member lists).** Compute and volume may fetch `volume.{cell}` routing tables of sibling
   cells **in the same DC** through `Relay.Routes`, for direct quorum traffic. Going through a Gateway would add a hop
   to every commit.
4. **B-21 readiness.** Add node-reported readiness, checked by the relay, for services whose ranges are not relay-fed
   (`volume`). This is a protocol change.
5. **AGENTS.md "Architecture boundaries"** must list `compute` and `volume` once S-03 lands.
6. **B-50** gains a step: send cron schedules to the Worker's cron actor on activation.
7. **Decision 11 and B-26 (#58): KV writers become actors (S-18).**

     and #58 is amended by comment. Customer KV has no write path until S-18. #71, #72 and #73 stay: v2 reuses the
     namespace directory, the read-only `Reader`, `ValueCache` and purge.

### S-19: load-based splitting (later)

Depot splits and rebalances its tablets by load. We start with B-15's assignment, which balances on each range's share of
the hash space. Random IDs spread actors evenly, so that share predicts load until a few hot actors share a range.

- **Balancing on stored bytes is in S-03** (changed 2026-11-14, so large volume clusters balance from the start). Each
  node publishes, in its member record, RocksDB's approximate size per range; S-05 adds the size of each range's SlateDB
  database from its manifest. `assign` balances on them. No new counters (about 2–3 days).
- **Gate.** Start the rest only when S-16 or production dashboards show volume nodes running hot while their range
  sizes are similar.
- **A bloated range** is detected from node-local signals published in the member record, never as metric labels:
  - size: bytes on SSD (S-03) and in the range database (S-05)
  - load: smoothed appends, reads and bytes written (below)
  - flush lag: how far the range database is behind the SSD log. It catches a range whose single SlateDB writer cannot
    keep up even when the range is small. (below)
- **Already there.** `assign` already splits ranges at any hash, moves them with a cap on concurrent moves, and keeps
  failure domains apart. `handoff` and `merges` complete the moves and rejoin ranges. Splits still go through the
  specified handoff, so no TLA+ change is needed.
- **New work, about 2–3 weeks for one developer:**
  - Volume nodes keep smoothed append, read and byte counters per range, in about 64 hash sub-buckets per range, plus
    each range's flush lag. They publish them in their member record, not as metric labels. (3–4 days)
  - `assign` takes these loads as input, and stays a pure function of the directory, membership and loads. It balances
    on measured load, splits where a range's load halves or its flush lag exceeds a bound, and uses hysteresis so
    ranges do not move back and forth. (4–5 days)
  - The split or merge of each range's SlateDB database is S-05's clone step.
  - A simulation workload with a few hot actors. (3–4 days)
  - Review and threshold tuning. (a few days)
  This replaces the drafts' 2026-10-31 estimate of 3–4 weeks, which was made before splitting and merging existed.
- **Limit.** One hot actor cannot be split: it is one hash with one writer. Splitting can only isolate it or move it to
  a quieter node. Isolated in a range of its own, it effectively has its own SlateDB database and writer, while small
  actors keep sharing.

### Acceptance highlights

- **S-02.** TLC checks `NoLostAck`, at most one open epoch serving writes, no stale-epoch append applied, and S3
  holding only committed entries. It models range handoff and a topology version change.
  - These negative checks must each break an invariant:
    - letting a `populating` slot vote
    - appointing a log that is not the most advanced
    - counting a previous-epoch entry as committed
    - flushing past the announced commit point
    - letting an unsealed leaving owner keep voting
    - committing with a majority of only the new slot set during a transition
    - claiming at an epoch the holder picked without reserving it (S-02b)
    - letting a repaired slot vote before a newer claim has committed (S-02b)
- **S-03 / S-04.**
  - Killing the holder or any one slot at every append boundary loses no acknowledged commit.
  - A commit is acknowledged after two fsyncs, with no S3 call.
  - A seed reproduces its trace.
- **S-05.** Overlay and log stay bounded while S3 is slow, with backpressure rather than loss. A flush followed by a
  crash before truncation does not apply anything twice.
  - S3 requests per flush interval do not grow with the number of actors in a range: creating many short-lived actors
    adds no S3 request beyond the range's flushes.
  - A range handoff copies no S3 data, and a split or merge by clone leaves every actor readable at its flushed
    sequence.
- **S-07 / S-08.**
  - A request to a sleeping actor wakes it on the wake host.
  - A request to an awake actor that has moved costs at most one redirect.
  - Two hosts racing to wake the same actor leave exactly one serving.
  - A holder cut off from its slots stops serving within 4 seconds.
- **S-09.** An alarm on a sleeping actor fires within 1 second of its time plus wake time. It fires again if the
  handler crashes before committing.
- **S-16.** Losing a cell in a three-cell DC loses no acknowledged write, and actors are available again within the
  lease time plus wake time.
- **S-18.**
  - A KV write in the home DC is acknowledged without an S3 call.
  - B-29's KV acceptance still passes, including a read at an acknowledged revision with no wait, `LIST` pagination,
    bulk atomicity and quotas.
  - A retried write returns its original revision and is not applied twice, also after the holder moves.
- **S-19.**
  - Under a skewed workload, every volume node's measured load ends within B-15's trigger of its target.
  - With steady load, no range moves twice in a row.
  - The cap on concurrent moves holds.
  - The same seed, directory and loads give the same plan.
  - A range whose flush lag stays above the bound is split or moved.
- **Metrics** carry only `cell`, `dc` and `kind` labels:
  - commit quorum latency
  - claim and wake latency
  - redirect count
  - lease expiries
  - flush lag
  - overlay bytes
  - alarm lateness

  Per-actor detail goes through introspection.

## 12. Open questions

1. **Sandbox runtime.** The user leans towards sandboxed workerd (2026-11-13, not final). The alternative is Node.js,
   OpenOrange's choice, which gives the full npm ecosystem but is heavier per instance. S-10 needs this decision. S-01
   to S-09 do not.
2. **Range databases (S-05).** Settled 2026-11-14 as one SlateDB per range (§5 Cold tier). Still to confirm in
   S-05, patching SlateDB if needed (the user accepts patches):
   - that the public clone API takes a key range for splits and several sources for merges (`clone.rs` has both
     internally in 0.17)
   - a key-prefix delete for actor deletion
   - how a range names its database across splits and merges
   - whether KV namespaces also move into range databases or keep `kv/{id}` and #73's per-namespace purge. Not decided.
3. **Page or chunk granularity** for the overlay, the cache and S3 keys. Measure in S-05.
4. **DC choice.** Placing a new actor near its first request, as Cloudflare does, instead of by `dc_of`, would need a
   region-level directory. Revisit only if measured latency demands it.
5. **KV durability option.** Should some namespaces wait for S3 before acknowledging, to survive losing a whole DC?
   It would be a per-namespace flag: the holder acknowledges only after the next flush, at about B-26's latency. Add it
   only if someone needs it.
6. **Large KV values.** Values up to 25 MiB, in bulk requests up to 100 MiB, are copied to three SSDs. The append
   window must be limited by bytes, not only by entry count. Measure in S-18.
7. **Heartbeat volume.** Heartbeats grow with (compute host × volume node) pairs that have actors in common. Measure in
   S-16. If needed, batch through each cell's Gateway.
